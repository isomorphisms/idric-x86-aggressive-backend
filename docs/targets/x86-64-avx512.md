# x86-64 + AVX-512 backend target

Branch: `target/x86-64-avx512`

This branch starts from `research/x86-isa-inventory`, so it inherits the complete pinned x86 reference: 1,987 XED ICLASS operations, row-level IFORM/encoding metadata, and grouped semantic Markdown. In that reference, the AVX-512/AVX10 bundle alone contains 770 ICLASS sections. This file records how a compiler should reason about an AVX-512 target rather than duplicating those 770 sections.

## AVX-512 is a capability set, not one switch

The minimum foundation is `AVX512F`, but many of the instructions most interesting for text/byte work live behind additional CPUID feature bits. Keep each capability independent in the backend.

Common extension groups include:

- **AVX512F** — foundation: 512-bit arithmetic, masks, many integer/floating operations, gathers/scatters, conversions, and the basic EVEX execution model.
- **AVX512DQ** — additional dword/qword integer and floating support.
- **AVX512CD** — conflict-detection operations.
- **AVX512BW** — byte/word vector arithmetic and comparisons; especially important for text processing.
- **AVX512VL** — apply many EVEX/mask operations to 128- and 256-bit vectors as well as 512-bit vectors.
- **AVX512IFMA** — integer fused multiply-add for 52-bit limbs.
- **AVX512VBMI** — additional byte/word permutations and multishift facilities.
- **AVX512VBMI2** — more byte/word permutation, compress/expand, and shift-related operations.
- **AVX512VNNI** — integer dot-product accumulate forms.
- **AVX512BITALG** — vector bit-algorithm operations such as byte/word population-count related facilities.
- **AVX512VPOPCNTDQ** — vector population count for dword/qword lanes.
- **AVX512BF16** — BF16 conversion/dot-product facilities.
- **AVX512FP16** — half-precision arithmetic on CPUs that actually expose it; **not implied by BF16 and not exposed by the current cloud runner**.

Other x86 extensions such as FMA, BMI1/2, AES, VAES, GFNI, PCLMUL/VPCLMULQDQ, SHA, AMX, and AVX10 are separate capabilities even when they frequently occur on the same machine.

## OS enablement

CPUID support is not sufficient by itself. The operating system must enable the relevant extended register state in XCR0/XSAVE state. The backend/runtime target check should therefore distinguish:

1. instruction capability reported by CPUID;
2. OS-enabled XMM/YMM/opmask/ZMM state;
3. any optional extension bit needed by the selected instruction.

A compiled fixed-target binary can instead make those requirements part of its deployment contract, but the contract must be explicit.

## Architectural resources

### ZMM vectors

AVX-512 extends the vector register model to 512-bit ZMM values. A 512-bit register holds, for example, 64 bytes, 32 words, 16 dwords, or 8 qwords.

Do not equate “AVX-512 target” with “always use 512-bit vectors.” EVEX + AVX512VL often permits the same mask-friendly operation at 128 or 256 bits. Width should be selected by measurements, surrounding data layout, register pressure, tail behavior, and the concrete CPU.

### Opmask registers

`k0`-`k7` provide explicit lane masks. This is the most important qualitative difference for our text/matching experiments.

Masks can:

- hold comparison results directly;
- guard arithmetic/data-movement lanes;
- enable zeroing or merge semantics;
- mask loads/stores for tails;
- be combined/tested without materializing a full vector of all-zero/all-one lanes.

The backend should represent masks as their own typed/width-aware value class rather than pretending they are ordinary integer vectors.

## Operation groups that matter most

The exhaustive ICLASS/IFORM list remains in `docs/instructions/avx512-and-avx10.md` and the generated XED tables. The following groups are the compiler choices that deserve explicit target logic.

### Mask-producing comparisons

Byte/word/dword/qword integer comparisons and floating comparisons can write directly to a `k` mask. For byte-oriented Bioawk work, `AVX512BW` is critical because `AVX512F` alone is not the complete byte-processing target.

Compiler effect: sixty-four byte equalities can become one mask value without a separate `VPMOVMSKB`-style reduction step.

### Mask tests and scalar control

Mask test operations can answer whether a mask is zero, all relevant bits are set, or intersects another mask. This is the natural bridge from lane-level comparison to one scalar branch.

Use them to compare:

- branch after every character;
- branch after every vector;
- branchless processing of a mask;
- enumerate only set bits when matches are sparse.

### Masked loads/stores and tails

EVEX masking makes safe short tails much easier when the exact instruction supports fault-suppressing masked memory behavior under the documented conditions.

Compiler rule: do not infer that every masked instruction suppresses every possible fault. Follow the specific XED/Intel/AMD semantics of the chosen form.

For string scanning, masked tail loads are attractive because they can eliminate a scalar cleanup loop while avoiding reads beyond the valid record.

### Compress/expand

AVX-512 families include compress/expand operations for supported element sizes/extensions. They can compact selected lanes or scatter them back into masked positions.

Possible uses:

- compact matching positions;
- compact qualifying quality scores/fields;
- process only selected lanes after a broad filter.

But compaction is not automatically cheaper than scanning a scalar bit mask. Benchmark both.

### Permute and byte-shuffle families

AVX512BW/VBMI/VBMI2 substantially improve byte/word rearrangement compared with AVX2. These can make table-like byte transforms and cross-lane rearrangements more natural.

Potential compiler uses:

- ASCII/DNA lookup transforms;
- packed nibble/byte table techniques;
- rearranging bytes for several motif positions;
- compact parser classifiers.

Do not use a sophisticated permute when several compares and Boolean operations are simpler and faster.

### Ternary Boolean logic

`VPTERNLOGD/Q` computes any three-input Boolean function under an immediate truth table. This can collapse several AND/OR/XOR/NOT operations into one vector instruction when the expression matches.

This is directly relevant to Shift-Or masks and multi-condition character classification. A target-specific Boolean simplifier can search for profitable ternary forms after semantic lowering.

### Conflict detection

`AVX512CD` can identify duplicate/conflicting indices inside a vector. It matters for vectorized hash/table/scatter algorithms, less obviously for linear string scanning.

Keep it in the inventory, but do not treat exotic availability as evidence that Bioawk needs it.

### Gather/scatter

AVX-512 extends indexed gather/scatter with mask control. These are useful for irregular table accesses, but contiguous scanning remains the natural first choice for FASTA/FASTQ bytes.

For lookup-heavy AWK operations, compare:

- scalar indexed accesses;
- small-table shuffle/permute techniques;
- gather/scatter;
- pre-expanded direct maps.

### Population count and bit algorithms

Where `AVX512VPOPCNTDQ` and `AVX512BITALG` are available, the vector machine can count selected bits/lane patterns directly. This can help batched bitsets, character-class summaries, and some matching formulations.

A scalar 64-bit mask plus scalar `POPCNT` is still a very strong baseline for 64-byte comparison results. Do not vector-popcount a mask that already fits in one scalar register.

### Vector neural-network integer dot products

`AVX512VNNI` supplies packed integer dot-product accumulate forms. These may matter for biological scoring kernels or compact numeric transforms; they are not a generic parsing primitive.

### BF16 / FP16

BF16 and FP16 are distinct target features with different numerical semantics and instruction sets. A backend should never select either solely because the source says “low precision.”

The current runner exposes AVX512BF16 but not AVX512FP16. That makes BF16 runnable here while native AVX-512 FP16 instructions should be treated as unavailable unless a different machine proves otherwise.

### Carryless multiply / crypto / GFNI

The current runner also exposes VAES, VPCLMULQDQ, and GFNI. These can be surprisingly useful for bit-matrix/finite-field transforms as well as cryptography, but they must remain separate optional extension paths rather than being silently folded into “AVX-512.”

For DNA/string matching, carryless multiply is worth an experiment only where the algorithm genuinely maps to polynomial/bitset operations.

## 256-bit versus 512-bit bakeoff

This branch should deliberately generate both widths where AVX512VL permits the same semantics.

Reasons 256-bit can win on some workloads/microarchitectures include:

- lower register pressure for surrounding scalar state;
- different implementation throughput/latency;
- more convenient alignment/tail structure;
- interaction with frequency/power policy;
- an algorithm whose natural block is already 32 bytes.

Reasons 512-bit can win include:

- twice the bytes tested per logical vector instruction;
- 64-bit comparison masks lining up neatly with scalar bit operations;
- fewer loop-control iterations;
- better amortization of address/control overhead.

None of those decides the result in advance. The benchmark is part of instruction selection.

## Branching experiments

AVX-512 gives us a particularly clean branch bakeoff:

1. scalar compare/branch;
2. compare tree or jump table;
3. AVX2-style vector compare -> scalar mask -> branch;
4. AVX-512 compare -> `k` mask -> mask test -> branch;
5. AVX-512 compare -> `k` mask -> predicated follow-up with no branch;
6. compare -> mask -> scalar bit iteration over matches;
7. masked compress/expand when selected lanes need dense processing.

Divergence is not a CPU SIMD issue in the same way it is on a GPU, but branch prediction, dependency chains, front-end bandwidth, and unnecessary work on masked-off lanes are still measurable costs.

## Bioawk-oriented candidates

### Record and field delimiters

A 512-bit load plus byte comparison can inspect 64 characters. The result is already a compact `k` mask. Use mask tests/bit scans to find `\n`, tab, comma, or another delimiter.

Compare against the AVX2 32-byte implementation rather than assuming 64-byte blocks win.

### Literal substring search

Candidate families:

- first/last-byte vector filter + exact verifier;
- aligned/shifted wide compares for short fixed motifs;
- mask intersections across pattern positions;
- Shift-Or/Bitap state, potentially using vector Boolean operations when multiple states/patterns are processed together;
- Boyer-Moore/Horspool skip logic with vector verification;
- VBMI/VBMI2 rearrangement only where it simplifies the actual verifier.

### Multi-delimiter and character-class classification

Comparisons can directly generate several masks (`is_A`, `is_C`, `is_G`, `is_T`, delimiter, whitespace, etc.). Mask Boolean logic can merge classes cheaply. This is a strong candidate for branch-free scanning.

### Quality-score loops

Byte/word masked arithmetic can process 64 quality bytes, while a threshold comparison can produce the exact positions failing or passing a criterion. Reduction should preserve the original algorithm's semantics; if the answer is “first failing position,” a scalar bit scan on the comparison mask may beat a full vector reduction.

## Current cloud runner capability profile

The current AMD EPYC 9V74/KVM runner exposes:

- `AVX512F`
- `AVX512DQ`
- `AVX512IFMA`
- `AVX512CD`
- `AVX512BW`
- `AVX512VL`
- `AVX512BF16`
- `AVX512VBMI`
- `AVX512VBMI2`
- `AVX512VNNI`
- `AVX512BITALG`
- `AVX512VPOPCNTDQ`
- plus AVX2, FMA, F16C, BMI1/2, GFNI, VAES, VPCLMULQDQ, AES, PCLMULQDQ, and SHA.

It does **not** report AVX512FP16 in the current guest feature set.

This should be recorded as a concrete benchmark profile, not mistaken for the abstract requirements of every AVX-512 machine.
