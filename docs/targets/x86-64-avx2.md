# x86-64 + AVX2 backend target

Branch: `target/x86-64-avx2`

This branch starts from `research/x86-isa-inventory`, so it already contains the complete pinned x86 inventory: 1,987 XED ICLASS operations, all recorded IFORM/encoding rows, and the grouped per-operation Markdown reference. This file is the **target-selection layer** for AVX2; it does not duplicate the complete architecture reference.

## Target contract

Minimum intended vector target:

- x86-64 user mode;
- SSE/SSE2 baseline implied by the ordinary x86-64 ABI environment;
- XSAVE/OSXSAVE state enabled sufficiently for AVX execution;
- AVX;
- AVX2.

Do **not** infer the following merely from AVX2:

- FMA;
- F16C;
- BMI1/BMI2;
- AES/PCLMUL/SHA;
- AVX-512 of any kind;
- vendor-specific instructions.

Those are independent feature gates. The backend can expose them as optional capabilities when CPUID plus OS state says they are usable.

## Register and execution model

- XMM registers expose 128-bit vector operations.
- YMM registers extend those architectural registers to 256 bits.
- AVX three-operand forms are valuable because the destination need not destroy either input.
- VEX-encoded 128-bit forms also participate in AVX upper-lane state rules; do not randomly mix legacy SSE and AVX encodings without understanding transition behavior.
- Vector width is an instruction-selection decision, not a source-language type identity. A semantic vector/string operation may be tiled into 128-bit or 256-bit chunks.

## AVX2 operation groups worth making explicit in lowering

The complete operation/form list is already in `docs/instructions/`; the groups below are the compiler-facing choices that matter most.

### Loads, stores, alignment, and tails

Representative families include `VMOVDQA`, `VMOVDQU`, scalar/vector load-store forms, lane insert/extract operations, and mask-based memory operations where supported by the relevant ISA set.

Compiler notes:

- Prefer unaligned-safe loads when alignment is not established by the IR.
- Prove or record alignment before choosing an aligned-only form.
- Avoid reading beyond the valid object merely because a 32-byte load is convenient; use scalar cleanup, a safely padded input contract, or another proven tail strategy.
- For streaming biological text, contiguous loads are usually a better starting point than gather.

### Integer addition/subtraction and saturation

Packed byte/word/dword/qword arithmetic includes ordinary and saturating forms. Signed/unsigned saturation is semantic, not an optimization hint.

Useful classes include packed add/sub, saturating add/sub, absolute value, min/max, average, and multiply families.

### Packed comparisons

AVX2 provides wide equality and ordered comparisons for supported integer lane widths. For byte-oriented text, `VPCMPEQB` is a central primitive: compare 32 bytes at once, then reduce the per-byte result to a scalar mask with `VPMOVMSKB`.

Compiler notes:

- Equality over bytes is particularly useful for delimiter scans (`\n`, `\t`, commas), DNA alphabet probes, and fixed-byte motifs.
- A mask is often more useful than immediately branching: combine several equality masks first, then branch once or enumerate set bits.

### Boolean and bitwise work

Packed AND/ANDNOT/OR/XOR plus shifts provide the ordinary bitset substrate. `VPTEST`/test-like forms can cheaply answer whether a vector mask has any relevant bits.

For Shift-Or/Bitap-style matching, the main question is whether the state fits naturally in scalar words, YMM vectors, or several independent scalar states. Do not vectorize a compact scalar bitset simply because AVX2 exists.

### Shifts and variable shifts

AVX2 adds broader packed variable-shift facilities beyond earlier SSE/AVX. These matter for bitset algorithms, lane-local indexing, and packed integer transforms.

Be careful about:

- lane width;
- signed versus logical right shift;
- immediate versus per-lane shift counts;
- operations that work independently inside 128-bit halves rather than across the full YMM value.

### Permutes, shuffles, blends, insert/extract

This group includes byte/dword/word shuffles, 128-bit-lane permutation, variable permutes for supported widths, blends, broadcasts, unpack/interleave, pack/narrow, and lane extraction/insertion.

Compiler notes:

- Many AVX2 rearrangements still have 128-bit-lane boundaries. Check the exact form before assuming an arbitrary 32-byte permutation.
- `VPSHUFB` is a table-like byte shuffle within 128-bit lanes and can replace small scalar lookup/branch structures when the lookup really fits its semantics.
- `VPERMD`/related variable permutes are useful for lane rearrangement, not a general byte gather.

### Broadcasts

Broadcast scalar or small memory values across a vector. Useful for comparing a byte/word/dword delimiter or constant against an entire loaded block.

The emitter should recognize “compare every lane against the same constant” as a semantic pattern and materialize the constant efficiently rather than reload a full literal vector.

### Horizontal operations, SAD, and reductions

Horizontal add/sub and sum-of-absolute-difference families can accelerate certain scoring/reduction patterns. They are less directly useful for exact byte matching than compare/mask/bit operations, but should remain candidates for quality-score or distance-like biological kernels.

### Multiply, multiply-add, and dot-like building blocks

AVX2 has packed integer multiply and multiply-add primitives. FMA is a separate feature, not part of AVX2.

For biological text processing these should be selected only where the source computation is genuinely arithmetic (quality-score transforms, numeric reductions, scoring matrices), not forced into parsing/matching.

### Gather

AVX2 introduces indexed gather for supported element widths.

Compiler note: gather looks attractive for table lookups but can lose badly to contiguous loads or scalar indexed loads depending on access pattern and microarchitecture. Treat it as an empirical candidate, never an automatic replacement for a loop.

### Widen/narrow/pack/unpack

Zero/sign-extension and packing operations are useful when ASCII/quality bytes need to become wider arithmetic lanes or when wide results can safely be narrowed again.

The type checker/IR should supply the proof of signedness and representable range; the backend should not guess.

## Branching and selection experiments

The branch experiment should compare at least these lowerings when the semantic operation permits them:

1. scalar compare + conditional branch;
2. short compare chain;
3. balanced compare tree;
4. table/indexed lookup;
5. indirect jump where appropriate;
6. branchless scalar mask/select;
7. 256-bit compare producing a bit mask, with one branch on the aggregate;
8. mask iteration using bit-scan/count operations when several matches in a block must be processed.

The interesting distinction is not “branching versus SIMD.” SIMD often **moves the branch outward**: 32 byte comparisons become one mask, followed by a much less frequent scalar branch.

## Bioawk-oriented first candidates

### Delimiter and record scanning

Load 32 bytes, compare against `\n` (and another delimiter if needed), convert comparison lanes to a bit mask, then use scalar bit operations to find delimiter positions. This is a straightforward correctness-preserving candidate for FASTA/FASTQ and AWK field scanning.

### Literal substring search

Keep several candidates alive:

- ordinary scalar baseline;
- wide first-byte or first/last-byte filter followed by verification;
- several shifted wide equality comparisons for short fixed motifs;
- Shift-Or/Bitap where the pattern length fits its state naturally;
- Boyer-Moore/Horspool-style skips for longer patterns;
- hybrid: vector filter plus scalar verification/skip logic.

No one strategy should be declared the AVX2 implementation before dataset measurements.

### Character-class tests

DNA/IUPAC alphabet checks, ASCII class tests, and delimiter families can often become a small number of vector compares plus OR/AND rather than one branch per character.

### Quality loops

Quality bytes are naturally packed. Subtract an offset, compare thresholds, accumulate or identify cut points using vector integer operations, then preserve the original scalar algorithm as the correctness oracle.
